# Windows transition to Avalonia

Plan recorded 2026-10-18 against Tasks `5637e3a`. This is an implementation/acceptance plan, not evidence that a Store replacement is ready. Avalonia receives active desktop development; Windows is the major target, Linux remains supported. WinUI receives necessary maintenance until retirement is explicitly accepted.

## Evidence boundary

The current Store host is WinUI. [`windows-continuation.md`](windows-continuation.md) records Windows Avalonia/Web source-build, interaction, pairing, backup/restore and schema-25 round-trip evidence at named PR snapshots. That evidence is valuable but does not cover an in-place WinUI Store → Avalonia upgrade, credential migration, native WinUI parity or live external-provider/OneDrive acceptance. No installed packages, account state or live data were inspected for this documentation baseline.

The Dev manifest does not match the agreed lane; record and resolve version ordering in the packaging slice, not by silently lowering an installed package's version. These are repository manifest values, not installed or latest Store versions. Preserve exact Store name/publisher association, application identity and supported architecture/OS constraints when preparing a replacement. The current manifests are x64 with minimum Windows build 19045. Do not copy private Store association metadata into new public documentation. Choose an eligible increasing version after checking actual packages; keep Preview/Dev isolated from Production.

Microsoft documents [package requirements and version selection](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/app-package-requirements). This supports checking generated packages and update eligibility; it does not prove that replacing this host preserves its data.

## Dev-first acceptance sequence

These steps describe future authorized execution. This documentation change does not authorize installation, package replacement, live-cloud operations or disruption of a daily app.

1. **Characterize and freeze fixtures.** On an isolated Windows test user or VM, install/build the existing WinUI **Dev** package. Use synthetic tasks across spaces/projects, dates, labels, completion and recurring source context; include settings differences, queued provider/cloud operations and restore points. Use synthetic/mocked credentials initially. Record exact source, package identity/version, resolved data paths and consistent pre-upgrade export/restore artifacts. Never use a daily-driver database or credential set.
2. **Implement continuity before replacement.** Test the path adapter, versioned settings conversion, bounded credential/cache migration and pairing-state handling in isolation. Use failure injection before/after each durable step. Retry must not lose original files or duplicate mutations. Keep a valid pre-migration safety copy; avoid reading only a SQLite main file while WAL writes are active.
3. **Exercise an actual Dev MSIX update.** In that same isolated environment, update the old Dev host to a higher-version Avalonia Dev package with matching Dev identity/publisher. Do not uninstall/reset first: that would avoid the continuity problem. Verify the generated package, update result and data actually opened. A fresh-install test is separate. If the agreed Dev lane cannot update the fixture version, resolve that packaging decision explicitly before the experiment.
4. **Compare semantics and platform behavior.** Capture/edit/complete/reopen offline, restart, verify counts/hierarchy/settings, then test duplicate/stale operations, sync resumption and restore into a separate isolated store. Never point WinUI and Avalonia at the same writable database for side-by-side comparison. Exercise second launch, GUI/CLI locking, title bar, file dialogs, browser sign-in, keyboard, scaling, high contrast and accessibility. Record Windows 10/11 coverage and any unsupported case.
5. **Validate real integrations only in approved test scope.** Separately verify provider silent sign-in/renewal, completion delivery, OneDrive backup/restore and Personal Cloud pairing/recovery against disposable/test accounts and deployments. Mock cache tests do not establish real authentication continuity. Confirm that secrets never enter logs, exports or screenshots. Retain the limits of the earlier Avalonia/Web evidence.
6. **Prove recovery and controlled rollout.** Test interrupted conversion and missing/revoked credentials. Retain consistent originals; do not open a migrated database with an older binary unless compatibility is proved. Recovery may require restoring the safety copy in isolation or a forward fix rather than an MSIX downgrade. After Dev acceptance, propose Preview validation with exact scope; existing Preview and Production are live daily apps and require explicit approval for disruption. Store submission, installation and release need their own authorization.

For each gate retain source SHA, before/after package identity/version, fixture description, checks/results, redacted screenshots and residual limitations. Repository tests and Linux builds support the gate but cannot substitute for a Windows package update.

## Retirement gates and remaining decisions

WinUI can retire only after documented behavior is covered by Avalonia, Windows platform acceptance is recorded, Dev upgrade continuity and recovery pass, necessary real integrations are verified in approved scope, and the user accepts the replacement/rollout plan. Keep WinUI source/build instructions until then; do not delete its host merely because the direction changed. A successful Preview experiment is not permission to replace Production.

Implementation decisions still needed: exact packaged data-path adapter, settings schema/mapping policy, credential compatibility mechanism and retention, Windows MSAL interaction choice, activation mechanism, packaging/signing tooling and version ordering, and supported rollback/forward-recovery procedure. None prevents this baseline from documenting the gaps. Stronger scheduled-session/recurrence semantics, reminder delivery and encryption/server capabilities remain separate product decisions ([behavior baseline](behavior-contracts.md)).

## Primary platform references

Checked 2026-10-18; apply them to a concrete package and verify again during implementation:

- [Microsoft: packaged desktop runtime and AppData virtualization](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes). Behavior depends on manifest/runtime type; do not assume a hand-built path bypasses virtualization.
- [Microsoft: Credential Locker](https://learn.microsoft.com/en-us/windows/apps/develop/security/credential-locker) and [PasswordVault API](https://learn.microsoft.com/uwp/api/windows.security.credentials.passwordvault). PasswordVault and Win32 generic credential targets are not an automatic migration bridge.
- [Microsoft: MSAL token cache serialization](https://learn.microsoft.com/en-us/entra/msal/dotnet/how-to/token-cache-serialization). Use supported callbacks and protected persistence; conversion needs application-level validation.
- [Microsoft: single-instance activation](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/applifecycle/applifecycle-single-instance) and [app notifications](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/). These establish platform mechanisms, not existing Avalonia integration.
- [Avalonia: Windows platform guidance](https://docs.avaloniaui.net/docs/platform-specific-guides/windows/). Windows builds are possible from other systems, but native interaction, signing and packaged upgrade acceptance still need Windows evidence. Built-in Fluent remains the baseline; no FluentAvalonia dependency is selected here.
